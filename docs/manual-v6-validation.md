# 手動v6（旧方式・現在は非推奨）

> **注意:** この文書は4PだけでMHまで自動起動する旧v6経路の履歴です。ユーザー実機ではMHが動かなかったため、現在の試験ブランチは3P側Humanフック `0x80150320` を使う二段階操作へ戻しています。現行の操作手順は [manual-controls.md](manual-controls.md) を参照してください。v6方式の「3P入力なしで両手起動」という記述は現行コードの操作説明として使わないでください。

対象は提供US 1.00 DOLとDolphin 5.0-21460。
手動版の開始処理を変更し、CPU用v4の通常版・確認版はバイト列を維持した。

## 提供設定と録画の確認

受領したGALE01.ini内の手動コードは、配布v5とSHA-256を含め完全一致。
有効なGeckoコードはそのv5とProper 16:9 Widescreen Support、
有効なARコードは3PのMH化・4PのCH化だった。
有効な併用コードによる開始フックの直接上書きは確認できなかった。
提供設定そのものはリポジトリへ収録しない。

録画では待機が続き、終盤に通常の拍手攻撃へ移る。
v5で補完した掴み判定に進む前の開始経路を変更する。
旧来の3P側の入力経路が実機で進まない原因自体は断定していない。

## 開始処理

`patches/manual_entry.s` をCHの移動完了時に呼ばれる待機初期化
`0x8015A114` へ接続した。元の4P入力処理は変更しない。

1. 4PのY＋十字右（入力値 `0x0801`）が要求ID380を登録し、ネイティブのCH移動を開始する。
2. 到着コールバックで要求380を確認し、MHが通常待機ならMH移動を登録する。
3. CH側は元の初期化を実行して状態384で待機する。
4. MH到着後の既存 `start_pair` が両手を状態385・380にし、掴み受付を初期化する。

MHが他の技を実行中の場合、CHの移動完了コールバックを維持して毎フレーム再確認する。
MHが不在・死亡・休眠中ならCHを通常待機へ戻す。
他の三つの連携要求は元の待機初期化へ渡し、3Pの入力で開始する挙動を維持する。

新フックは関数引数r3にCHのGObjを受け取るため、展開ローダーでもr3を保存・復元する。
初回の確保・展開時とキャッシュ済み時の両方を確認した。
v5の判定補完・二人目の命中履歴更新・握りダメージ・音・投げは維持している。

## 検証

`tests/test_native_startup.py` では、以下を提供DOLのPowerPC命令で連続実行する。

- Human/CPUの分岐を含むCHの通常待機処理と、4PのY＋十字右（入力値 `0x0801`）の入力処理。
- 実際の手の検索、CH移動登録と到着コールバック。
- 生成C2フック、ローダーと展開後コード、MH移動登録と到着コールバック。
- 両手の状態変更要求、ネイティブINIT_GRABによる受付・マスク・拘束コールバック登録。

3P入力をゼロにしたまま、要求380→CH移動→MH移動→両手の掴み初期化へ到達する。
MHが別の技を実行中の場合、他の三つの連携要求、キャッシュ再利用、不在・死亡・休眠も検証した。
既存の二人拘束・判定・ダメージ・解放の項目と合わせ、55項目成功。

この検証はアニメーション読込と状態適用を代替し、到着時の移動残量をゼロに設定する。
フレーム全体の物理・描画・音声出力を再現するものではない。
別のネイティブ判定テストで、球とカプセルの重なり・チーム除外・拘束受付を確認している。
Dolphinでの入力から投げまでの実動作と、参考映像との完全一致は未確認。

## 配布と容量

- `dist/Tagtsukamu-US-1.00-manual.txt`：3144バイト。
- SHA-256：`b575944d5ecac079e4e0b95b8eed54f093d712dca0d6eb14e7bf434c3b3e41ec`。
- [Dolphin公開設定](https://github.com/dolphin-emu/dolphin/blob/master/Data/Sys/GameSettings/GALE01r0.ini)
  の同名ワイドスクリーンコード88バイトを併用した場合、合計3232バイト。
  既定コード領域の上限3256バイト以内。

提供INIから作成する差し替え用ファイルでは、旧v5の定義・有効名だけをv6へ交換する。
その他のコードと有効状態を保持する。ゲームを完全停止して交換し、旧ステートを使わず起動する。
発動操作は**4PのY＋十字キー右（入力値 `0x0801`）のみ**。
