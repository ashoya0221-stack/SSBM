# 手動v8：P3/P4の実際の手の種類を見て選択

対象：スマブラDX US 1.00 / Dolphin 5.0-21460。

## 変更の目的

v7では、Master HandをP3（slot 2）、Crazy HandをP4（slot 3）と固定して取得していた。
実際のVersusでP3/P4の割り当てが逆になっていると、要求と別の手を取得してしまう。
その結果、別のアクション番号が適用され、意図したTagtsukamuの演出にならない可能性がある。

## v8の変更

手動版の `get_hand_manual` だけを変更した。

1. P3（slot 2）のPlayer_GetEntityを呼ぶ。
2. 戻ったGObjのfighterデータ（GObj+0x2C）の種別（+4）を確認する。
3. 要求種別（Master Hand=27 / Crazy Hand=28）と一致すればP3を返す。
4. 一致しないかP3が空ならP4（slot 3）を取得する。

この補正は手の取得先だけに適用する。技の本体は変更しない。

- Master HandのTagtsukamu：action 385 / motion 339
- Crazy HandのTagtsukamu：action 380 / motion 334
- 握り・ダメージ・投げ・効果音・判定補完の処理はそのまま維持。
- CPU用通常版・確認版の検索処理は変更しない。
- 4PのY＋十字キー左でCHを動かし、到着後にMHを呼び出す操作も維持。

## 検証

PPCランタイム内の手動検索関数は20命令・80 bytesのままにし、既存ランタイム内の他コードや相対参照先を移動させずに差し替えた。
Gecko C2データを再圧縮し、ランタイム長0xFC0、Player_GetEntity呼び出し先0x80034090、C2ブロックの件数と展開結果を再確認した。

起動テストには通常のP3=MH/P4=CH配置に加え、P3=CH/P4=MHの逆配置を追加した。
逆配置でも要求種別に一致する手が選ばれ、MH=385 / CH=380の状態で両手の掴み初期化に到達することを検査する。
P3が空でP4だけがCHの場合、CHをMHとして誤って開始しないことも検査する。

## 制限

Player_GetEntityの戻り値はテスト内サービスで置き換えている。これは検索関数の分岐と手の種類の判定の検査であり、Dolphin上での通常Versus実機テストではない。
実際の対戦で意図した技になるかは、新しいコードを使って確認する必要がある。
