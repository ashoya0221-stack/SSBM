# 通常Versus手動版：v4コア＋P3/P4プレイヤー枠検索

## 基準にした実装

技本体はCPU用v4と同じソース `patches/tagtsukamu.s` と `config/restoration.json` を使用する。
投げ開始はv4で採用した**212フレーム**。241フレームへ戻さない。
手動開始経路は、後のv6/v7/v8で追加された「4P到着時に自動でMHを呼ぶ」フックではなく、
v5当時のHuman入力経路に戻す。

## 通常Versus向けの差分

手動ビルドで使う共有手検索ルーチン内の3箇所について、fighter kindで検索する `GET_HAND` を
通常のプレイヤースロットから取得する `Player_GetEntity` に差し替える。

- Crazy Handの検索引数：fighter kind 28 → P4 slot 3
- Master Handの検索引数：fighter kind 27 → P3 slot 2
- US 1.00のPlayer_GetEntity呼び出し先：`0x80034090`
- US版1.00のHuman入力側はCHの要求値 `0x2250` に380を書き込む。手動版の開始条件も380を確認する。

CPU用通常版・確認版の検索処理と開始条件は変えない。手動版ではHuman経路用フックとP3/P4の手検索を追加するが、
技のアクションID（MH=385、CH=380）、投げ212フレーム、掴み・握り・投げ・音・衝突処理は変更しない。

## US版1.00で確認した要求値

提供されたUS版1.00の `main.dol` を直接逆アセンブルして確認した。

- CH側の人間入力処理 `0x801565B4` は `li r0,380`、`0x801565CC` はその値を `0x2250` に書き込む。
- CH到着コールバック `0x8015A114` はモーション384へ変更する。
- MH側の人間入力処理 `0x80150250` はCHの要求値を読み、380の場合は欠けている4番目の分岐 `0x8015030C` へ進む。
- その分岐の最後の命令 `0x80150320`（`stfs f0,0x18(r1)`）を、手動版の入口フックとして利用する。
- `Player_GetEntity` は `0x80034090`。P3はslot 2、P4はslot 3として検索する。

前回の383は、公開されている別バージョンの列挙値をUS版1.00へ誤って適用したものだった。今回それを撤回し、手動版の条件を380に戻した。CPU用v4の条件も380のまま維持する。

## 掴まれたファイターの追従

通常Versus手動版の捕獲成立時に、捕獲側の手Fighterと相手Fighterを渡して、
US 1.00のネイティブ関数 `0x800DAF1C` を呼ぶ。通常の掴み処理 `0x8009C7CC` を照合し、引数順を **手側Fighter、相手Fighter** とする。この関数は相手のモデルルート
（`FtPart_XRotN`）を手側の `FtPart_TransN2` へ拘束し、元のルート位置を保存する。

続けて相手Fighterの `accessory1_cb`（`+0x21B0`）へ、独自の
`sync_captured_fighter` ラッパーを設定する。ラッパーはまずネイティブ位置
コールバック `0x800DB018` を呼び、拘束されたモデルルートからFighterの
`cur_pos`（`+0xB0`）を更新する。その直後にUS 1.00の
`Player_80032828`（`0x800327A8`）を呼び、同じ座標をPlayer管理側の現在の
変身スロットへ書き戻す。

この追加が必要なのは、ネームタグの座標がFighterの `cur_pos` ではなく、
Player管理側の座標を読むためである。US 1.00のネームタグ更新経路
`0x802FB4C0` は `Player_LoadPlayerCoords`（`0x8003264C`）を呼ぶ。
通常の同期処理 `0x8006D900` は `Player_80032828` に `cur_pos` を渡すが、
`is_sleeping` フラグが立っている場合はその同期を飛ばす。捕獲中にもタグを
追従させるため、専用ラッパーで同じ同期を明示的に行う。

Playerスロット（Fighter `+0x0C`）、サブファイター番号（`+0x221F` のbit）、
座標ポインタ（`+0xB0`）は、US 1.00の通常Player同期処理と同じ引数構成にする。
特にPlayerスロット番号は1バイト値なので、`lbz r3,0x0C(r30)` で読み取る。
通常の `Fighter_procPlayer`（`0x8006D900`）も `lbz r3,0x0C(r31)` を使って
`Player_80032828` へ渡している。前の候補にあった `lwz r3,0x0C(r30)` は
4バイト読み込みであり、隣接フィールドまでPlayer番号として渡す誤りだったため修正した。
この誤りがゲーム内での不具合の原因だった可能性はあるが、Dolphinでの再現・解消は未確認。
従来の捕獲枠・握り・投げ・212フレーム設定は変更しない。
ネームタグ同期用の相対ポインタを挿入したことで移動する `attach_captured_done` への
NULL分岐は、生成されたPPC分岐先がラベルと一致することをテストで確認する。

この追加は手動Human入力版だけに含め、CPU用v4と連携確認版の生成内容は維持する。
DOLの `0x800DAF1C` と `0x800DB018` の入口バイト列をUS 1.00の照合項目へ追加した。解除側も確認し、US 1.00の `0x800DC614` から `lb_8000C390`（ルート拘束の解除）を呼び、`+0x2226` の拘束フラグをクリアすることを照合した。既存の `CAPTURE_CUT` 経由で解除される設計で、独自の解除フックは追加していない。
解除・投げを含む一連の挙動は、追加版をDolphinで実際に確認する必要がある。

## 静的確認と制限

v5手動版の2段階入力経路とv4ランタイムを基に、次を維持・修正した。

- 共有手検索の3箇所をPlayer_GetEntityによるP3/P4検索へ変更。
- 手動入口はUS版1.00のマスターハンドHuman側欠落分岐 `0x80150320` を使用。
- CHのHuman入力要求値は、US版1.00で実測した380を使う。CPU版v4も同じ380で、どちらも変更しない。
- 手動版の掴み補完を維持。

今回の生成コードの静的数値は次のとおり。
- 展開ランタイム：4,000 bytes
- 圧縮データ：2,771 bytes（4 byte境界へ整列した領域は2,772 bytes）
- Geckoコードリスト：3,184 / 3,256 bytes
- 手動入口C2ブロック：383ペア
- 圧縮データを展開し、修正後ランタイム4,000 bytesと一致することを確認
- Player番号の命令：`0x887E000C`（`lbz r3,0x0C(r30)`）
- 捕獲対象がNULLのときの分岐先：`attach_captured_done` ラベル

Human入力要求値380、到着モーション384、手動フック `0x80150320`、
P3/P4のPlayer検索、投げ開始212フレームは維持している。
別技へ自動で切り替えるv6以降の到着フックは使用しない。

## 完成判定に必要なDolphin確認

以下はコードの仕様・確認項目であり、この候補版ですべて実証済みという意味ではない。
現時点でDolphin上の追従追加版は未確認。

1. 4PのY＋十字キー左、続けて3PのY＋十字キー上でプレイヤー操作から発動する。
2. 発動後にマスターハンドが正しい位置へ移動し、クレイジーハンドと連携する。
3. 実際のステージ上で掴み判定が成立し、握り・投げ・床との衝突後の復帰まで進む。
4. 掴まれたキャラクターのモデルとネームタグが、手の中で同じ位置へ自然に追従する。
5. 指定したTagtsukamu以外の技へ化けず、通常操作でも誤発動しない。

Keystone・Unicornがこの実行環境にないため、PowerPC実行テストハーネスは未実施。
Dolphin実機テストも未実施。前提となる380版ではプレイヤー発動と投げの再現を
ユーザーが確認済みだが、今回の追従追加版は別ビルドであり、その結果を流用しない。
上記5項目をこの同一コードで確認するまでは、完成・動作保証・マージ済みとは扱わないこと。
