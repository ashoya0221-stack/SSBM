# 通常Versus手動版：v4コア＋P3/P4プレイヤー枠検索

## 基準にした実装

技本体はCPU用v4と同じソース `patches/tagtsukamu.s` と `config/restoration.json` を使用する。
投げ開始はv4で採用した**212フレーム**。241フレームへ戻さない。
手動開始経路は、後のv6/v7/v8で追加された「4P到着時に自動でMHを呼ぶ」フックではなく、
v5当時のHuman入力経路に戻す。

## 通常Versus向けの差分

手動ビルドで使う共有手検索ルーチン内の3箇所について、fighter kindで検索する `GET_HAND` を
通常のプレイヤースロットから取得する `Player_GetEntity` に差し替える。

- Crazy Handの検索引数：fighter kind 28 → P4 slot 3
- Master Handの検索引数：fighter kind 27 → P3 slot 2
- US 1.00のPlayer_GetEntity呼び出し先：`0x80034090`
- US版1.00のHuman入力側はCHの要求値 `0x2250` に380を書き込む。手動版の開始条件も380を確認する。

CPU用通常版・確認版の検索処理と開始条件は変えない。手動版ではHuman経路用フックとP3/P4の手検索を追加するが、
技のアクションID（MH=385、CH=380）、投げ212フレーム、掴み・握り・投げ・音・衝突処理は変更しない。

## US版1.00で確認した要求値

提供されたUS版1.00の `main.dol` を直接逆アセンブルして確認した。

- CH側の人間入力処理 `0x801565B4` は `li r0,380`、`0x801565CC` はその値を `0x2250` に書き込む。
- CH到着コールバック `0x8015A114` はモーション384へ変更する。
- MH側の人間入力処理 `0x80150250` はCHの要求値を読み、380の場合は欠けている4番目の分岐 `0x8015030C` へ進む。
- その分岐の最後の命令 `0x80150320`（`stfs f0,0x18(r1)`）を、手動版の入口フックとして利用する。
- `Player_GetEntity` は `0x80034090`。P3はslot 2、P4はslot 3として検索する。

前回の383は、公開されている別バージョンの列挙値をUS版1.00へ誤って適用したものだった。今回それを撤回し、手動版の条件を380に戻した。CPU用v4の条件も380のまま維持する。

## 掴まれたファイターの追従

通常Versus手動版の捕獲成立時に、捕獲側の手Fighterと相手Fighterを渡して、
US 1.00のネイティブ関数 `0x800DAF1C` を呼ぶ。通常の掴み処理 `0x8009C7CC` を照合し、引数順を **手側Fighter、相手Fighter** とする。この関数は相手のモデルルート
（`FtPart_XRotN`）を手側の `FtPart_TransN2` へ拘束し、元のルート位置を保存する。

続けて相手Fighterの `accessory1_cb`（`+0x21B0`）へ
ゲーム標準の `0x800DB018` を直接設定する。このネイティブ位置コールバックは毎フレーム、
拘束されたモデルルートからFighterのワールド座標（`cur_pos`）を更新する。
ただしネームタグはPlayer管理側の座標を読むため、この版ではタグの位置は同期されず、
元の出現位置に残る場合がある。ネームタグ同期用の独自ラッパーは意図的に含めない。
従来の捕獲枠・握り・投げ・212フレーム設定は変更していない。

この追加は手動Human入力版だけに含め、CPU用v4と連携確認版の生成内容は維持する。
DOLの `0x800DAF1C` と `0x800DB018` の入口バイト列をUS 1.00の照合項目へ追加した。解除側も確認し、US 1.00の `0x800DC614` から `lb_8000C390`（ルート拘束の解除）を呼び、`+0x2226` の拘束フラグをクリアすることを照合した。既存の `CAPTURE_CUT` 経由で解除される設計で、独自の解除フックは追加していない。
解除・投げを含む一連の挙動は、追加版をDolphinで実際に確認する必要がある。

## 静的確認と制限

v5手動版の2段階入力経路とv4ランタイムを基に、次を維持・修正した。

- 共有手検索の3箇所をPlayer_GetEntityによるP3/P4検索へ変更。
- 手動入口はUS版1.00のマスターハンドHuman側欠落分岐 `0x80150320` を使用。
- CHのHuman入力要求値は、US版1.00で実測した380を使う。CPU版v4も同じ380で、どちらも変更しない。
- 手動版の掴み補完を維持。

基準の380版は6,876 bytes、C2ブロック367ペア、Geckoコードリスト3,056 bytes。ネームタグ同期を含まない本切り分け版は7,056 bytes、C2ブロック377ペア、Geckoコードリスト3,136 bytes。どちらもDolphinの上限3,256 bytes以内である。本切り分け版は120 bytesの余裕を残す。
基準版の展開ランタイムは3,780 bytes、圧縮ストリームは2,637 bytes。本切り分け版は3,904 bytes、圧縮ストリームは2,724 bytes（4 bytesのゼロパディング）。さらにPlayer座標同期ラッパーを加えた現在の候補は4,000 bytes、圧縮ストリーム2,770 bytes（2 bytesのゼロパディング）となる。各候補の展開サイズ・圧縮境界をGeckoデータから再確認した。
本切り分け版では `attach_captured` のNULL分岐は `attach_captured_done`（ランタイムoffset `0xF10`）へ到達し、runtime末尾の分岐も `runtime_exit`（`0xF2C`）へ到達する。捕獲関数の引数順は手側Fighter、相手Fighter。US 1.00の要求値380と投げ212フレームは維持している。v4の技本体、CPU版の処理は変更していない。

US版1.00の `main.dol` のハッシュ・バイト照合に、Human CHの要求値380、CH到着時のモーション384、
MHのHuman側4番目分岐、フック位置 `0x80150320`、`Player_GetEntity` の入口を追加した。
テストハーネスにも380を受け入れて383を拒否するケースを追加した。

Keystone・Unicornがこの実行環境にないため、既存の全テストハーネス／PowerPC命令実行テストは未実施。今回の追従追加版については、US 1.00 DOLの2関数入口、分岐先、スタック領域、圧縮展開、Gecko容量を静的確認した。
従来の380版ではDolphin通常Versusで発動・投げが再現することをユーザーが確認済み。追従追加版そのものは未プレイのため、掴み中のモデル・ネームタグ追従と投げ・解放後の復帰をDolphinで確認するまでマージしないこと。
